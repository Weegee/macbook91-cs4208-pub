Upstream-derived sources: what is fetched, from where, and why
==============================================================

Nothing described in this file is stored in the project's repository. It is
a specification: packaging/fetch-upstream.sh reads it as prose and implements
it as code, and every file below is reconstructed at package build time.

Origin:  git.kernel.org  linux/kernel/git/stable/linux.git
Tags:    one per kernel series, pinned in packaging/upstream.lock. With no
         flag (or --all) the script takes the newest lock tag of every series
         (today v6.18.55 and v7.2.6). Each --tag names one series explicitly;
         --kver or $KDIR resolve a single tag from the UTS_RELEASE of the
         headers they point at: 7.2.6-1-cachyos -> v7.2.6, and 7.2.0-1-cachyos
         -> v7.2, because kernel.org tags the first release of a series
         without the trailing .0. Two tags for one series are refused.

Fetched verbatim, and nothing else ever is, once per series <S> (6.18, 7.2):

  upstream/<S>/cs420x.c           sound/hda/codecs/cirrus/cs420x.c
  kheaders/<S>/hda_local.h        sound/hda/common/hda_local.h
  kheaders/<S>/hda_auto_parser.h  sound/hda/common/hda_auto_parser.h
  kheaders/<S>/hda_jack.h         sound/hda/common/hda_jack.h
  kheaders/<S>/hda_beep.h         sound/hda/common/hda_beep.h
  kheaders/<S>/generic.h          sound/hda/codecs/generic.h

The kernel paths are the same in both series. The lock rows use the
series-independent names upstream/cs420x.c and kheaders/*.h, keyed by tag.

Derived from them, offline, by patch --forward --fuzz=0:

  <S>/cs420x.c                upstream/<S>/cs420x.c + local-changes.patch
  vendored/a1534_sequence.h   vendored/ORIGINAL-a1534_sequence.h
                              + vendored/a1534_sequence.patch

The second derivation reaches no network at all. The A1534 bring-up trace is
a permanent part of this repository and of the package, and is not downloaded
from anywhere, ever. See vendored/PROVENANCE.md.

Why the headers are fetched at all
----------------------------------
They are private kernel headers, and no headers package installs them:
linux-cachyos-headers puts Kconfig files under sound/hda/ and nothing more.
Measured, not assumed. cs420x.c includes them, so they have to come from
somewhere, and the kernel's own git is the only primary source. This is the
single download in the whole build.

What guards it
--------------
packaging/upstream.lock records a sha256 for every (tag, file) pair. A pair
it does not know is refused; a pair it knows whose bytes have changed is a
hard failure with no override, because the same tag returning different bytes
is not a version bump. --accept-new is how a new tag is admitted, and it
never overwrites a pair already recorded.

--fuzz=0 on both patches is deliberate. A patch that still applies
"approximately" after upstream moved a function is how a silent behavioural
change gets into a driver; here it stops the build instead.

Inside the assembled tree, UPSTREAM.sha256 and vendored/PROVENANCE.sha256
travel with the files and are checked by the Makefile's `check` target before
anything compiles. They establish integrity of the installed copy, not
origin - a manifest generated beside the files it describes cannot say where
they came from. packaging/upstream.lock is what says that.

kheaders/KERNEL-SERIES lists the series the headers were fetched for, one per
line. The Makefile derives the series of the target kernel from its
utsrelease.h and builds the matching <S>/cs420x.c with kheaders/<S>/; a series
not in the list is refused, because these are internal structure definitions
with no ABI promise. dkms.conf carries the same set in BUILD_EXCLUSIVE_KERNEL,
so DKMS skips other kernels instead of failing them. Adding a series means
admitting its tag to the lock and rebuilding the package, not overriding the
check.

Local modifications to cs420x.c are listed in LOCAL-CHANGES.md and are kept
as small and as clearly delimited as possible.
