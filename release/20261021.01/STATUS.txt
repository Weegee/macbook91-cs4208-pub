macbook91-cs4208-dkms 20261021.01-1 - RELEASE (first public release, tagged v20261021.01; comments, attribution, licence headers and non-code files only, no driver behaviour change; hardware result carried over, NOT RUN for this version)

What changed: comments in the files the source tarball is built from were
reworded for a public reader, attribution and licence headers were added, and
the documentation was rewritten for readers without access to the
maintainer's machines and names the early 0.x versions in one place only. No
executable line was added, removed or changed. The two derived cs420x.c files
change by comments only, through local-changes.patch,
so packaging/upstream.lock pins new hashes for them (v6.18.55 and v7.2.6 stay
the pinned kernel.org tags). The source identity string of the module changes
anyway, because it hashes files whose comments changed: 7.2 3459bbf7be37223c
(was 79b16c8b296a3821 in 20261020.03), 6.18 2fc8b8ad2d1b2deb (was
7fc96add428d9fce). The full list is in docs/CHANGELOG.md.

Identity proof, measured without hardware on 2026-10-21 (VERIFIED): the source
tarball of this release was compared with the 20261020.03 tarball.
- Every changed C file (the two derived cs420x.c and four headers) is
  identical to 20261020.03 once comments are stripped (gcc -fpreprocessed -dD
  -E -P), line for line.
- The three ACP and WirePlumber .conf files differ in comment and blank lines
  only, the root Makefile and the changed tools/ scripts in comment lines
  only; local-changes.patch differs in comment lines only; packaging/upstream.lock differs in the two derived cs420x.c pins and in
  one comment (it no longer says that 6.18 was not yet run on hardware).
- vendored/ORIGINAL-a1534_sequence.h, vendored/a1534_sequence.h and
  vendored/a1534_sequence.patch are byte-identical; the only added file is the
  licence sidecar of the vendored original.
- The module was built from both tarballs at one fixed build path, unprivileged
  and without installing anything, against 7.2.11-1-cachyos (clang) and
  6.18.55-2-cachyos-lts (gcc). The sections of both kernels' modules are
  identical except the source identity string in .modinfo, the build id and,
  for the clang build, six source-file checksum slots in .debug_line. Code, data
  and symbol sections are byte-identical; of the sections the kernel loads
  (SHF_ALLOC), only .modinfo and .note.gnu.build-id differ. The checksum
  slots hold md5 sums of source files (the earlier run of this proof matched
  each slot to a changed source file; the last run, step V8 of the
  verification driver, counted the slots and did not repeat that match). The
  build id is
  expected to be a hash over the module's contents, so it follows from the
  changed identity string (inference, not checked separately). Neither is
  code.
